# Weekly Radar Runtime Implementation Plan

> For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

Goal: Add a real Weekly Radar runtime that collects the approved free evidence stack, publishes a deterministic report to Telegram every Monday 09:00 JST, and keeps a one-year rolling archive on the dedicated data branch.

Architecture: Keep the existing Domain/Application/Interface boundaries provider-neutral. Add a runtime module with injected HTTP, source adapters, deterministic rule extraction, report assembly, Telegram transport, and data-branch archive helpers. The CLI composes these pieces; the workflow owns Git branch reconstruction and rolling orphan-commit push.

Tech Stack: Rust 2021, serde/serde_json for public-source payloads, ureq for synchronous HTTP, regex for rule extraction, chrono for ISO date and retention arithmetic, GitHub Actions with actions/checkout@v5.

## Global Constraints

- No paid data API dependency in v0.
- No LLM extraction; ambiguous facts are UNKNOWN.
- Primary evidence outranks secondary evidence; GDELT is discovery-only.
- Provider-specific types stay under src/features/weekly_radar/runtime.
- Every normalized fact retains source URI, source field or passage, retrieval time, effective date when available, and status/confidence.
- Monday schedule is exactly 0 0 * * 1 UTC, equivalent to Monday 09:00 JST.
- Telegram reads ORGX_TELEGRAM_BOT_TOKEN and ORGX_TELEGRAM_CHAT_ID only from runtime environment.
- SEC reads ORGX_SEC_USER_AGENT and never requires a paid key.
- Archive output is on branch data, never a data/ directory on main.
- Retention is 365 days; only data history may be compacted.
- Tests use fixture HTTP transports and never call public endpoints, Telegram, or GitHub.
- Resolve in-scope defects in WI-WR-016 instead of opening a new WI.

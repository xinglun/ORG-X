# WI-WR-016 Weekly Radar Runtime Design

## Goal

Turn the existing provider-neutral Weekly Radar boundaries into a runnable weekly
research pipeline. The runtime collects official and free public evidence,
preserves provenance, produces deterministic Markdown and Telegram messages,
stores a bounded one-year history on the dedicated data branch, and fails
closed when required configuration or publication safety conditions are not met.

## Non-negotiable constraints

- No paid data API dependency in v0.
- No LLM extraction. Deterministic rules only; ambiguous facts are UNKNOWN.
- Primary evidence outranks secondary evidence.
- GDELT is discovery-only and never authoritative without official corroboration.
- Provider-specific types stay in runtime infrastructure and do not enter Domain.
- Every normalized fact retains source URI, source field or passage, retrieval time,
  effective date when available, and status/confidence.
- GitHub Actions runs every Monday at 09:00 JST using 0 0 * * 1, and supports
  workflow_dispatch.
- Telegram credentials are read only from ORGX_TELEGRAM_BOT_TOKEN and
  ORGX_TELEGRAM_CHAT_ID.
- SEC access requires ORGX_SEC_USER_AGENT.
- The data branch is the only archive target. No data/ directory is added to main.
- Each run retains the latest 365 days of data. The data branch is rebuilt as
  a rolling snapshot so its reachable history does not grow without bound.

## Architecture

    CompanySourceRegistry
            |
            v
    Provider-neutral HTTP boundary
            |
      +-----+--------+-------------+-------------+
      | SEC/XBRL     | Official    | Greenhouse  | Lever/GDELT
      | submissions  | pages       | public jobs | public/discovery
      +-----+--------+-------------+-------------+
            |
            v
    Raw observations + deterministic rule extraction
            |
            v
    Normalized Fact { status, provenance, confidence }
            |
            v
    Weekly Radar runtime report
            |
       +----+-------------------+
       | Markdown + Telegram   |
       | Snapshot + Receipt    |
       +----+-------------------+
            |
            v
    Rolling data-branch archive (365 days)

The Domain remains a read-only decision boundary. Runtime facts are assembled
outside Domain and passed to the existing publication/rendering boundaries as
opaque, precomputed values. The runtime does not assign Stage, score companies,
or infer an organization change from missing evidence.

## Runtime boundaries

### runtime/config.rs

Loads and validates config/weekly_radar/companies.json.

The registry is versioned and contains company identity, ticker, optional SEC
CIK, and optional official IR, Careers, Engineering/AI Blog, Greenhouse board,
and Lever site references. Optional sources are explicit configuration; absent
references produce UNAVAILABLE, not guessed URLs.

### runtime/http.rs

Defines an injected synchronous HttpClient used by all adapters:

    pub trait HttpClient {
        fn get(
            &self,
            url: &str,
            headers: &[(String, String)],
        ) -> Result<HttpResponse, RuntimeError>;
    }

The production implementation uses a small synchronous HTTP client. Tests use
an in-memory fixture transport. Errors are typed and never include secret
values.

### runtime/sec.rs

Implements SEC submissions and Company Facts/XBRL acquisition:

- data.sec.gov/submissions/CIK##########.json
- data.sec.gov/api/xbrl/companyfacts/CIK##########.json
- latest configured 10-K primary document when employee text extraction is needed

The adapter sends the configured ORGX_SEC_USER_AGENT, selects the latest
annual facts using explicit form/fiscal-period/duration rules, and preserves
the concept name, unit, filing accession, filing date, report date, source URL,
and raw structured value.

The initial deterministic concept aliases cover Revenue, Operating Income,
Net Income, Operating Cash Flow, CapEx, R&D, SBC, and Employee Count. If no
unambiguous alias/value is available, the fact status is UNKNOWN.

### runtime/rules.rs

Extracts employee-count candidates from filing or official-page text without an
LLM. A candidate is accepted only when:

- the number is syntactically adjacent to an employee phrase;
- the passage identifies the company workforce rather than customers or a
  different population;
- the effective date is explicit or inherited unambiguously from the filing;
- there is exactly one supported candidate for the requested period.

Approximate language is retained as an approximate fact. Conflicting,
multiple, date-less, or semantically unclear candidates become UNKNOWN with
the rejected passages retained in diagnostics.

### runtime/sources.rs

Implements configured official-page fetches, public Greenhouse and Lever
postings, and GDELT discovery. Each output is a source observation with
authority tier and provenance. Greenhouse and Lever are parsed only when a
board/site is configured. GDELT records title, URL, publication date, and
query context with a discovery-only status.

### runtime/report.rs

Builds a deterministic weekly report from explicit normalized facts. It emits:

- report metadata and as-of date;
- per-company financial and workforce facts;
- hiring/source coverage;
- UNKNOWN, UNAVAILABLE, and UNCONFIRMED sections;
- source links and evidence passages;
- a System Health summary describing source coverage and extraction failures.

The report uses the existing known top-level headings required by the semantic
Telegram splitter. The runtime does not compute Stage, ranking, or investment
claims.

The human-facing Telegram layout is intentionally mobile-first and scannable:

- `## Executive Summary` opens with the period/as-of date, one plain-language
  conclusion, and no more than three short bullets covering what changed, why
  it matters, and the data status.
- `## Important Structural Change` contains at most three numbered cards. Each
  card is limited to `Company — signal/status`, `Why it matters`, and
  `Evidence: source label + URL`.
- `## Top5` contains at most five compact company cards with explicit facts and
  signals. It must not invent Stage, rank, score, or investment conclusions.
- `## System Health` closes with source coverage, UNKNOWN/UNAVAILABLE/
  UNCONFIRMED counts, discovery-only notices, data age, and items that need
  review. Primary-source links appear here when they are not already attached
  to a card.

Content uses short labels (`CONFIRMED`, `UNKNOWN`, `UNAVAILABLE`, and
`DISCOVERY ONLY`), bullets rather than tables, and short paragraphs. The first
Telegram chunk must answer “what changed, why it matters, and what evidence
supports it” within roughly 30 seconds. Only the existing recognized top-level
headings are used so semantic chunking remains safe; additional detail belongs
under `###` subheadings. Markdown is conservative and every chunk remains
within Telegram's message limit, split only between semantic sections.

### runtime/telegram.rs

Provides a production TelegramTransport implementation that calls Telegram's
Bot API with a JSON sendMessage request. It uses the existing publisher and
semantic splitter, preserving exact chunk order and typed partial receipts.
The transport reads token/chat ID from environment only and redacts both from
errors. Fixture tests use a recording transport and never make network calls.

### runtime/archive.rs

Writes a run to an archive root with stable names:

    weekly-radar/
      reports/YYYY-MM-DD.md
      snapshots/YYYY-MM-DD.json
      receipts/YYYY-MM-DD.json
      manifest.json

Before writing, it removes only files whose date prefix is older than the
configured retention window (default 365 days). It refuses a non-data branch
when invoked in guarded mode. The GitHub workflow then creates a new orphan
commit from the retained tree and force-updates only data; this deliberately
forgets reachable Git history older than the retention window while preserving
the retained files.

### runtime/mod.rs and src/main.rs

org-x weekly-radar parses the runtime flags:

- --as-of YYYY-MM-DD
- --archive-dir PATH
- --registry PATH
- --dry-run

It loads the registry, acquires sources, normalizes explicit facts, renders,
optionally publishes, writes the archive, and returns a non-zero result for
required configuration/report/publication failures. Dry-run never sends
Telegram or mutates the archive.

## Workflow

.github/workflows/weekly-radar.yml:

- triggers on schedule 0 0 * * 1 and workflow_dispatch;
- uses actions/checkout@v5;
- grants contents: write because the workflow writes only data;
- uses a concurrency group to prevent overlapping data-branch compaction;
- runs the Rust CLI with ORGX_SEC_USER_AGENT and Telegram Secrets;
- reconstructs the current data tree if it exists;
- runs retention and report generation;
- creates a rolling orphan commit and updates data with a guarded force push;
- does not upload long-lived Actions artifacts. Any optional diagnostic artifact
  uses short retention.

## Failure behavior

- Missing SEC User-Agent, registry, or Telegram credentials: fail before send.
- Individual optional source unavailable: preserve UNAVAILABLE and continue if
  the report still has a valid structure.
- No primary evidence for the configured universe: emit an explicit health
  failure and do not publish.
- Invalid or oversized Markdown/chunks: fail before transport invocation.
- Telegram partial failure: retain the existing typed receipt and do not claim
  a successful publication.
- Data-branch mismatch, protected branch rejection, or stale force-push lease:
  fail without touching main.

## Verification

The implementation uses fixture-driven tests for:

1. registry validation and optional-source semantics;
2. SEC concept selection, User-Agent propagation, filing provenance, and
   employee passage extraction;
3. rule-only employee positive/ambiguous/unknown cases;
4. Greenhouse, Lever, official-page, and GDELT parsing;
5. deterministic report rendering and Telegram semantic splitting;
6. redacted Telegram failures and exact ordered delivery;
7. 365-day archive retention and data-branch guard behavior;
8. CLI dry-run and failure gates;
9. workflow schedule, Secrets, contents:write, checkout@v5, and no
   checkout@v4.

No test calls public HTTP endpoints, Telegram, or GitHub.

# Weekly Radar 人类可读报告设计

## 目标

把 Weekly Radar 的 Telegram 输出从运行诊断改为面向读者的周报：读者先看到本周结论、确认过的变化和需要注意的缺口；采集器、状态枚举、来源编号和完整逐项清单只保留在 data 分支的 snapshot 中。

## 输出契约

- 默认语言为简体中文（`zh-CN`）。支持显式选择日语（`ja`）或英语（`en`）。同一输入与语言必须产生字节稳定的 Markdown。
- 摘要使用“本周结论 / 重要变化 / 数据状态”这类读者词汇，不直接展示 `source_*`、`CONFIRMED`、`UNAVAILABLE`、`UNCONFIRMED` 或 `0/10` 等内部表示。
- 没有确认过的主证据时，明确写“本周没有可作为主证据的确认信息”，不拿失败项或未确认线索冒充证据。
- 重要变化只展示已确认的结构变化；新闻、招聘和其他未确认材料只作为“待核实线索”计数，不升级为结论。
- 数据状态按来源类型和影响归纳：可用、暂不可用、尚未配置、仅作发现线索。每个聚合项保留可行动的公司数量和简短原因。
- snapshot 继续保留完整事实、状态、来源、逐项 review item 和采集失败，供追溯和后续处理；Telegram 不重复这些内部细节。

## 运行边界

- `ReportLanguage` 和 CLI `--language` 只控制展示语言，不改变事实、排序、来源权威或抽取规则。
- `workflow_dispatch` 提供 `language`、`as_of`、`dry_run`；定时任务默认使用 `zh-CN`，dry-run 不发送 Telegram、不写 data 分支。
- 可选 Greenhouse/Lever 缺少配置时使用独立的 `NOT_CONFIGURED` 采集状态；已配置但请求失败仍是 `UNAVAILABLE`。
- SEC 单家公司失败不会丢失整个运行的诊断；失败原因只使用已脱敏的错误类别，不输出请求头、响应体或环境变量。
- Telegram 语义分割器接受三种语言的章节标题，确保本地化不破坏消息拆分。

## 不做的事

不在本次 WI 中引入排名、阶段推断、LLM 抽取、付费 API、新闻权威化或新的外部数据源。
